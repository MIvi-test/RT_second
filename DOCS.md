### 1. Синтаксический анализ и чункование (AST-парсер)
Скрипт рекурсивно обходит директорию `gymhero` и обрабатывает исключительно файлы с расширением `.py`.
* Для разбора структуры кода используется стандартный модуль `ast` (Abstract Syntax Tree). Это позволяет делить код не по количеству символов, а по логическим границам: **классы**, **методы внутри классов** и **функции верхнего уровня**.
* Пути файлов вычисляются строго через `Path.relative_to(repo_root)`. Это гарантирует формирование валидных идентификаторов вида `gymhero/subfolder/file.py:name:lineno` без дублирования родительских папок, что критично для валидации в `score.py`.

### 2. Векторизация текста (Генерация эмбеддингов)
Текст каждого извлеченного компонента трансформируется в векторное представление.
* За векторизацию отвечает модель `paraphrase-multilingual-MiniLM-L12-v2` из библиотеки `sentence-transformers`.
* На выходе для каждого чанка генерируется вектор плотных эмбеддингов фиксированной размерности **384**. Разбор и кодирование происходят пакетами (`batch_size=32`) в оперативной памяти.

### 3. Инициализация и заполнение ChromaDB
Сгенерированные данные переносятся в локальную векторную базу данных.
* Скрипт инициализирует `chromadb.PersistentClient` по пути `./chroma_db`.
* При каждом запуске существующая коллекция `code_chunks` принудительно удаляется (`client.delete_collection`) во избежание дублирования ID при повторных тестах.
* Создается чистая коллекция со строгим указанием метрики расстояния: `{"hnsw:space": "cosine"}` (косинусное сходство).
* База данных заполняется порциями по 200 элементов, куда одновременно записываются: `ids` (путь:имя:строка), `embeddings` (массивы float), `documents` (исходный текст кода) и `metadatas` (тип объекта, имя, файл).

### 4. Обработка исключений и завершение
Весь процесс обернут в блоки `try-except`. При возникновении синтаксических ошибок в коде приложения (`SyntaxError`) дефектный файл пропускается. При критических сбоях (отсутствие датасета, сбой инициализации модели или базы) выполнение прерывается через `sys.exit(1)`. При успешной записи всех чанков процесс возвращает `sys.exit(0)`.

Данные проверки будут сокращены и исправлены на моменте сборки(контейнеризации) проекта. Сохранится только бизнес логика.

# Реализация Search

## 1. Изменение index.py

- **Инъекция метаданных (Metadata Injection).** Главная проблема поиска по коду — потеря контекста. Векторная модель не понимает, откуда взята функция. Мы решили это, приклеивая путь к файлу и имя класса прямо в текст чанка перед векторизацией:  
    "document": f"File path: {rel_path}\nObject type: ... \nCode: ..."
    
- **Специальный токенизатор для кода (tokenize_code).** Стандартный BM25 разбивает слова по пробелам. Наш токенизатор разбивает camelCase и snake_case (например, create_user → create, user), что критически повысило точность полнотекстового поиска.
## 2. Поисковый движок (search.py)

Здесь реализована логика поиска. Написано два метода: semantic_search и hybrid_search.

**Как это работает:**
1. **semantic_search:** Идет в ChromaDB, по смыслу достает Топ-75 кусков кода, а затем отдает их Реранкеру, который выставляет финальные баллы и возвращает Топ-5.
2. **hybrid_search:** Берет кандидатов из ChromaDB (смысл) и из BM25 (точные слова), смешивает их с весами (0.6 векторы / 0.4 текст), берет Топ-30 лучших и отдает Реранкеру.

**Зачем нам Реранкер (Cross-Encoder)?**  
Обычные векторные модели сравнивают "вопрос" и "ответ" по отдельности. Реранкер BAAI/bge-reranker-v2-m3 принимает на вход одновременно (Вопрос пользователя, Код функции) и анализирует их совместимость через механизм Attention.  
Результат: Реранкер понимает, что "create a new account" = функция register:55. Это дало нам огромный буст метрики на сложных вопросах.

## 3. Выбор модели

В целом сейчас это не очень важно, но на данный момент в коде стоят мощные "тяжеловесы" для максимизации метрики:

- Эмбеддинги: intfloat/multilingual-e5-large
- Реранкер: BAAI/bge-reranker-v2-m3
